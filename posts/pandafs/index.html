PandaFS: Distributed File System in Go

Posted on 2023-11-21 • 777 words • 4 minute read
Tags: distributed-systems, projects
Check out the project on GitHub!

Distributed systems are all about pessimism and paranoia. What if my hard disk gets fried? What if my computer explodes? What if a million people all request for the same file and my website breaks for 2 minutes?

While these scenarios may sound a little far-fetched, these are very real concerns for enterprises serving thousands or even millions of customers around the clock. Downtime causes a huge loss of revenue, and data loss is catastrophic to say the least.

Creating a robust and efficient file system is a significant challenge when you want it to survive the apocalypse. This blog chronicles the development of a distributed file system in Go, which I (not so) lovingly call PandaFS.

So what is a DFS anyway?

A regular file system is simple enough - your computer has storage (hard disk platters or NAND flash chips) that physically stores data, and you have bundles of bytes (files) that you want to store. A file system not only handles the space management part, but also allows you to store your files under directories so you have some form of structure to help keep you sane.

A distributed file system is the same thing, but instead of just being restricted to a single disk or multiple disks on the same computer, we store files across multiple computers, all part of a network (usually the internet). These computers are called nodes and together they’re called a cluster.

This allows us to replicate our files (or fixed-size blocks of our file) across multiple nodes and create a fault-tolerant system. If some nodes go down, we just fetch the other replicas stored on other nodes instead. This makes the system highly available, and scalable. We can simply make the system move effective and have higher storage if we add more nodes to the cluster.

How do I build one?

There’s a couple major components of a DFS, depending on the complexity of what you’re implementing. PandaFS rips off directly from HDFS, but with less features because I have a skill issue.

First off, you obviously have the nodes themselves, these are of two types: The namenodes (called masters in PandaFS), and the datanodes (called mules in PandaFS). The mules actually store the bytes that the user really cares about in the form of blocks, and the masters store data about the data, like the name, size, and filepath.

For the sake of simplicity, we don’t handle master node failure at all, and assume the mules are the only ones that fail. The way this is handled in HDFS is there’s redundant namenodes that is used in tandem with the ‘primary’ one, so when it fails, the other ones pick up the slack. Unless it was pre-Hadoop 2, which just went belly-up on namenode failures. So look forward to master redundancy in PandaFS 2 I guess.

We do account for mule failures though, simply because there are a lot more of them. Each mule contains blocks of a fixed size - 128 MiB. This is to account for files that are straight up too big for a single machine or disk (a very real concern when dealing with Big Data). Each block is copied to n different nodes - where n is the replication factor, 3 by default. This allows us to access files even when a node (or 2) storing the file crash.

How do we know when a mule crashes? We use our stethoscope, of course (it’s a heartbeat sensor)! The stethoscope is a process running on the master that periodically receives heartbeat messages from the mules, letting it know that they are still working fine. If the master doesn’t receive the message within a certain interval, it assume the mule crashed, and the system works without it.

This entire replication and splitting-into-blocks process is abstracted away from the user, who only sees a single cohesive file system, thanks to the master’s metadata representation.

Speaking of the user, they also need a way to interact with the FS. This is done through a CLI client that supports standard metadata commands like touch, rm, mv, cp, and mkdir.
